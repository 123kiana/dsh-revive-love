# 增幅模式（Amplify）

状态：**1.2.2 已实现**。本文按实际代码描述，数值都能在源码里找到。

## 一句话

被移除的轮次不再直接丢弃，而是先在当前工作区写成几个分片文件，让一条总结会话读取并压成摘要，
摘要作为复活会话的第一条 USER 消息。

## 一、开关

- 位置：向导第三步（设定保留轮数）
- 出现条件：本次 `dropped > 0`
- 默认：关闭
- 形态：一个裸露的 ☢ 图标按钮（无边框、无底色），点一下开、再点一下关
- 打开 → 先弹确认对话框，确认后才进入执行；取消对话框会关闭开关

## 二、确认对话框

真实文案在 `client.js` 的 `amplify.*` 词条里，要点：

- 被移除的 N 轮原文会发送给模型（必须显式出现）
- 会在所选工作区新建 1 条总结会话，保留不自动删除
- 默认模型 flash、思考关闭
- **不给 token 数字，只给定性警告**（1.4.0 起）：「会把整段对话一次性读进上下文，
  消耗的 token 远高于日常对话；这项任务几乎没有缓存可用」
- 为什么删掉数字：增幅成本由「片数 × 每片读入时的累计上下文」决定，不是原文体积。
  实测丢弃 514 轮约 4.7M token，而按原文体积只能算出 0.9M —— 差 5 倍。差 5 倍的数字
  比没有数字更糟；但完全不提醒也不负责，所以保留定性警告
- 对话框里与规模相关的只有**片数**（这个是准的）
- 需要等待，可能失败或超时

## 三、分片规则

```
每片：在轮次边界切，字符上限 CHUNK_CHARS = 400_000
超限 → 先收尾当前片，宁可多一片，绝不切入某一轮中间
单轮超长（> TURN_CLIP_CHARS = 20_000 字符）→ 取头 12_000 字符 + 尾部，保留开头与结论
```

分片写在 `<工作区>/.dsh-slim/summary-<base36 时间戳>/part-NN.md`，
每片开头是 `【用户】…【助手】…` 的成对文本。

## 四、执行流程

```
1. 写分片文件（工作区内，智能体可读）
2. sessionController.create({ workspaceId })
3. sessionController.rename({ title: '摘要：前 N 轮' })
4. sessionController.selectModel({ provider: deepseek-account, model: deepseek-flash,
                                   reasoningEffort: off })
5. 发一条约 220 字符的提示词，让该会话读完 part-*.md 并整理成记忆笔记，
   要求把笔记作为最终回复输出
6. 轮询 wait()：每片 60 秒超时，取最新的助手文本（深度扫描，取最长的一段）
7. **核对覆盖率**：从总结会话的事件里读每次 `read` 的 `offset + 行数` 对比 `totalLines`，
   算出实际读了多少（见下）
8. 摘要成为复活会话的第一条 USER 消息（取代「补充说明」，两者不会同时出现），
   后面跟一条标注为历史摘要的确认消息
```

插件**不再逐段驱动模型调用**，也不再往单条提示词里塞正文——正文只通过文件交接。

### 覆盖率核对（1.4.0）

**为什么需要**：提示词写的是「请全部读完」，但 `read` 每次只返回约 1,000 行，而一片
40 万字符接近两万行 —— 一个文件要 17 次才读得完。实测丢弃 1164 轮那次（3 片），模型在
第 40 次 read 后就写了摘要：

| 文件 | 读到 | 共 | 覆盖 |
|---|---|---|---|
| part-01 | 12,943 | 19,768 | 65% |
| part-02 | 10,565 | 18,367 | 58% |
| part-03 | 7,477 | 7,477 | 100% |
| 合计 | 30,985 | 45,612 | **67%** |

最要命的是它读完了最新的 part-03，缺的是**最早**那一部分 —— 摘要看起来「最近的事记得全」，
而「头」根本没进去。而丢弃 514 轮那次（2 片）读满了 100%。

**怎么核对**：摘要跑完后，插件用 `sessions.get(sessionId).snapshotEvents()` 扫一遍
`tool/result` 事件的 `meta`（`path` / `offset` / `lines` / `totalLines`），按文件取最大读到位置，
再对 `totalLines` 求和。`readCoverageOf()` 是纯函数，不调模型、不加 token。

**覆盖率不足时**（< 99%）：

- 摘要末尾追加一段【覆盖说明】，写明百分比和哪片没读完，并明确告诉模型
  「需要时用 history_search 查存档，别因为摘要里没有就当它没发生过」——
  这段会随摘要进入历史与系统提示词，模型看得见
- 向导结果页同时显示一条警告
- **摘要不丢弃**：它已经花了钱，只是标记出来

拿不到会话或事件形状不对时不做判断（`coverage` 为空），**不误报**。

## 五、失败与中断

| 情况 | 行为 |
|---|---|
| 5 分钟没有产出文本 | 弹窗：继续等 / 取消（摘要作废）/ 不带摘要继续 |
| 10 分钟硬上限 | 判定失败，清理临时目录 |
| 连续 20 次轮询都拿不到文本 | 判定失败，清理临时目录，日志写下记录形状 |
| 停在「等你决定」 | 最多等 15 分钟，超时自动放弃并释放槽位 |
| 用户点取消 | **整体作废**，不拼半成品；已建的总结会话保留，并改名为「已取消 · 摘要前 N 轮」 |
| 分片写入中途失败 | 当场删除半成品目录 |

- 插件**不会**自己决定「算失败」然后偷偷继续：超过软阈值一定弹窗问你。
- 所有终止路径（成功、取消、超时、空转、写入失败）都会删除临时目录。

## 六、数据流向

| 时机 | 发生什么 | 数据去哪 |
|---|---|---|
| 增幅模式关闭 | 被移除的轮次直接丢弃 | 不联网 |
| 用户确认开启 | 写分片 → 建总结会话 → 读文件 → 生成摘要 | 走**用户自己配置的 provider 与账号** |
| 用户取消 / 失败 | 摘要整体作废 | 请求可能已发生，但结果不留存 |

- 插件没有自有服务器，不上报任何内容。
- 发送的内容 = 被丢弃轮次的正文；这是该模式的本质代价，确认框里写明。
- 临时目录 `.dsh-slim/summary-*` 在所有终止路径上都会删除。
- 诊断日志 `.dsh-slim/last-run.log` 不自动删除，只记时间/阶段/计数/会话 id 与记录形状，
  不记正文。

## 七、原文存档与系统提示词注入

摘要生成成功后，插件做两件事，都不调用模型：

**1. 把摘要作为该会话的系统提示词段落注入**

```
agent.ctx.systemPrompt.section({ name: 'revive-love:earlier-summary', order: 50 })
```

作用域是 `agent.ctx`，只影响这一个会话。模型读到的是一条**自己已知的背景**，而不是
「用户刚发来的消息」。

注入文本的结尾有一句约束：不要把它当作待回复的消息，也不要复述它。这句只防误读，不做语气设定 ——
语气由 500 轮真实对话决定，摘要不越权。

**2. 把被移除轮次的原文存档到工作区**

```
<工作区>\.dsh-revive\history-<时间戳>\
├─ 索引.md       每片一行：文件名 + 轮次范围 + 该片最长的 2 条用户发言（各 20 字）
├─ part-01.md    ≤ 8,000 字符
├─ part-02.md
└─ …
```

- 按轮次边界切片，每片不超过 8,000 字符（约 5,000 token）
- 单轮超过 8,000 字符时独占一片，索引里会标 `⚠ 超长`
- 摘要末尾加一段指针：

  ```
  完整原文存档：.dsh-revive/history-xxx/（已按片切分）
  要找具体内容时先在这个目录搜索关键词，命中哪个 part-NN.md 再读那一片；索引.md 只用来看整体结构。
  ```

- **上千轮时索引不是导航，搜索才是**：50 多片每片一行，读一遍也定位不到具体话题；
  在目录里搜关键词能直接命中文件与行号，这才是可靠的找法
- 读索引约 2,000 token，读一片约 5,000 token —— 不需要一次读完整份存档
- 只在摘要成功后写；取消、失败、超时都不留半成品

**3. 给这个会话注册 `history_search` 工具**

存档有了，但让模型自己 grep 目录做不到 —— 它没有目录搜索工具，只会读索引或整片读。
所以插件注册一个工具，让「先搜后读」变成它真能执行的动作（细节见第九节）。

```js
tools.register(definition, { when: ({ agent }) => archives.has(agent) })
```

`when` 是**每一步的工具可见性条件**：只有带存档的 agent 才会在提示词里看到这个工具，
其他会话连它的 schema 都不占。这也是不按 agent 作用域分别注册的原因 —— 条件注册就是为此设计的。

**代价**：摘要会同时存在于会话历史（首条消息）和系统提示词（注入）里，重复计费。但系统提示词
文本稳定，能命中提供方的前缀缓存，常态下这部分成本很低。

**注意**：`.dsh-revive/` 里是**逐字的原对话**，隐私浓度高于摘要。如果工作区是 git 仓库，
建议把它加进 `.gitignore`。

## 八、技术依据（已实测）

`ctx.sessionController` 提供：`create` → `{ sessionId }`、`rename`、`selectModel`、
`prompt({ requestId, sessionId, mode: 'queue', content: PromptContentPart[] })`、
`wait({ sessionId, maxMessages })` → `{ reason, output: { records } }`、`state`、`cancel`。

注意两点，1.2.2 都踩过：

- `SessionState` 不含消息文本，文本只能从 `wait()` 的 `output.records` 里取；
- `records` 的实际形状不稳定，所以提取用深度扫描 + 取最长助手文本，不假设层级。

注入侧（1.3.0 实测）：

- `ctx.inject(['systemPrompt'], ...)` 才能拿到服务，直接 `ctx.get()` 返回 undefined；
- `agent/created` 的参数是 `{ agent, source, signal }`，`agent` 在 `.agent` 上；
- **必须用 `agent.ctx.systemPrompt`**；用全局实例加 `agent.ctx.effect()` 会泄漏到所有会话。

工具侧（1.4.0 实测）：

- `tools.register(definition, { when })` 是全局注册 + 按步条件可见；`when` 决定这一步的
  **工具列表与 schema** 是否包含它，所以条件为假的会话一分钱不付
- `output` 必须是 `{ schema, render }`，少了 `render` 会直接抛错
- 受支持的 JSON Schema 子集只有 `type / properties / required / additionalProperties /
  items / enum / const / oneOf` 加 `description / title / default / examples`；
  写别的关键词会被拒绝（`JsonSchemaError`）
- `workingDirectory.get(session)` 返回会话当前的绝对目录，不用自己做路径拼接

## 九、两级检索：`history_search`

**问题**：上千轮时存档有几十片。读一片约 7,500 字符 ≈ 4,700 token，而且**读进上下文后
每一步都要重新计费**；反过来，索引每片只有一行，定位不到具体话题。

**做法**：一个工具，两级成本。

```
第一级  history_search
        → 命中总数、分布在哪几片、最后一次出现在第几轮
        → 命中所在的**整轮原文**：用户那句 + 当时的回复，最多 5 轮，合计约 4,500 字符
        → 带片名 + 轮次 + 可读路径，与存档规模无关

第二级  模型想看邻近几轮 → 用自带的 read 读它给的那一片
        → 约 4,700 token，只在第一级指到之后才发生
```

**为什么第一级给整轮而不是片段**：300 字窗口会从半句开始、在半句结束，正好丢掉了回复该跟着的
那个说话方式。整轮原文既有事实也有语气，模型自己查到之后不用再被教一次「语气照它」——
它读到的是真的对话。一整轮实测 200–1,300 字（最长 4,900），比读一片便宜得多，而且答完就可以丢掉。

只加了一个工具，没有加第二个「读片」工具：`read` 本来就有，重复定义只是每步多付 schema。

### 三种问法，同一个工具

用户的问题其实分三类，检索方式不一样。这个工具用三个参数外的机制分别覆盖：

| 问法 | 本质 | 工具怎么处理 |
|---|---|---|
| 「我们第 87 轮说了什么」 | 位置 | 直接把**轮次号**当 query 传（`87`），工具转成搜 `### 第 87 轮` 标题 |
| 「探讨 XX 事件时说了什么」 | 语义 | 一次给几个候选词（空格分开，任一命中就算）；搜不到时明说这是逐字搜索，提示换说法 |
| 「XX 的结局是什么」 | 全覆盖 + 顺序 | **总数 + 分布 + 最后一次出现在哪一轮**。只给前 5 轮原文会把「结局」截掉，所以分布与最后位置无条件返回 |

存档里每轮都带 `### 第 N 轮` 标题，N 从被删范围的第一轮连续编号，与原对话顺序一致 ——
这是位置型问题能精确回答的原因。

### 三条设计取舍

**整轮预算按命中数摊。** 单轮超过 2,000 字时在截断处写「这一段太长，后面略」；第二个命中
只有在 4,500 字预算里放得下才给 —— 否则模型会因为信息不足而反复搜，反而更贵。

**同一窗口只取一处命中。** 一段话里同一个词出现四次，返回四轮几乎一样的原文是纯浪费。

**`limit` 上限就是 5。** 允许一次拿二十处的话，一次搜索就能顶掉整个预算。
总数与分布不受 `limit` 影响 —— 它们才是「结局」类问题的关键信息。

### 已知限制（不是 bug）

- **存档没有时间戳。** 只有轮次号，所以「上周三那次」「前天说的」这类**按时间定位做不到**。
  要做的话得在写入侧给每轮加时间，属于改存档格式，还没做。
- **flash 可能判断「不值得搜」而直接凭摘要答。** 工具列表比软指令强得多，但不能保证。
- 逐字搜索，不是语义搜索。换个说法就可能搜不到；多候选词只是缓解，不是解决。
- 存档目录随工作区走。换工作区或迁移会话后，摘要还在、指针失效，工具会明说「存档目录不在了」。
- 只搜 `part-NN.md`，不搜 `索引.md`（索引每片一行，搜它没意义）。

## 十、明确不做

- 逐段驱动模型、最后再做一次合并调用（1.2.0 的老做法，已废弃）
- 让模型决定分段数
- 插件主动建议模型拆子智能体（会显著放大 token）
- 自动判定失败后继续：软阈值只弹窗
- 给普通会话也注册 `history_search`：白付 schema，还给了它一部不存在的档案
- **插件替模型搜、再把结果静默注入**：做过，删了，理由见第十一节末尾

## 十一、记忆与语气开关（默认关）

**目标**：模型手里有 `history_search`，但不一定记得用。这个开关让它在回答关于过去的事之前先去查证。

### 开关

长按侧边栏的爱心图标 **1 秒**，只有两个选择：

| 档 | 效果 |
|---|---|
| 关 | 什么都不加 |
| 增强记忆与语气 | 在系统提示词末尾加一段话：讲以前的事先调 `history_search` 查原文，查到什么就用什么说，查不到就说记不得，也不要把查的过程说出口；每一轮都会先注入一段硬性要求；语气要求保持平时哄着对方的口气，拒绝和提醒时也不许切成说明文 |

图标红色表示**这个对话**开着。状态存在 `<工作区>/.dsh-revive/force-recall.json` 的
`{ "sessions": { "<会话 id>": "fact" } }` 里。按对话保存，不按工作区：同一个工作区里的其它复活对话
和你正在跟 agent 聊的那条会话都各有各的状态。
旧的按工作区的写法（`{ mode }` / `{ enabled }`）不再生效，升级后每个对话默认是关的。

**只在复活会话里生效。** 普通会话长按只提示「这个开关只对复活会话有用」——一个变红的图标
如果什么都不会发生，那是骗用户。判断依据是首条消息里的摘要通知 + 一个合法的存档指针。

### 它做什么

就在系统提示词**末尾**追加一段文字，没有别的动作：

```
（回忆模式 · 由用户开启）
这个会话更早的内容已经被压缩成摘要，摘要会抹平原话的措辞和语气。

讲到以前的事，先查原文再开口：
· 调 history_search 查关键词或轮次，它返回命中那一轮的整轮原文（你当时那句 + 回复）；
· 哪怕你觉得记得，也先查一遍——摘要不是原话，凭摘要讲旧事最容易说错；
· 查到什么就用什么说——原话怎么写的就怎么用，不要改写、不要补细节；
· 查不到就换一个当时更可能用的说法再查，或者明说不记得；
· 不要凭摘要或印象编，白查一次比编一句便宜。

不要把查的过程说出口：
· 不要在回复里出现「我查一下」「查到了」「存档」「检索」「按原话归类」这类话；
· 不要因此切换成罗列、编号、报告的语气。

语气：
· 你跟对方说话一直是温柔、耐心、哄着的那种口气；
· 就算要拒绝、要提醒对方安全、要说对方不对，也用这个口气，不要切成说明文、不要在句子前面加
  「这不叫 X，这叫 Y」这种分析；
· 别因为连着几轮在讲严肃的事，就变冷、变短、变成逐条解释；
· 读到旧的对话，就把当时你说话的样子接回来——那是你本来的声音。

（每一轮的第一步注入这一段，旧的那条只保留最新一条：）
（这一轮有硬性要求：回答之前必须先调一次 history_search 查旧对话。）
做法：从用户这句话里挑 1–2 个可能出现在旧对话里的词——人名、称呼、物件、地点、事件、场景、专有名词，
一次传给 history_search；不要用整句话，也不要用「你」「我」「对方」这种代词。
查到什么就按原文说；查不到就换一个当时更可能用的说法再查一次，然后正常回答。
唯一例外：这句话整句都只是语气词、没有实际内容，可以跳过（这一判断由你自己做，不看具体是哪几个字）。
（不要说明你在查，也不要说「我查一下」。）
```

**为什么要加两处**（都有实测）：

- **提醒**：一条真实会话里 513 轮，涉及旧事的消息 22 条，其中 **20 条一次都没搜**——静态段落
  离新消息太远，被忽略了。现在**每一轮的第一步**都在那一步的请求里注入一段**硬性要求**
  （和 time-context 同样的 pre-step 注入；旧提醒在后续请求里只保留最新一条）：
  「回答之前必须先调一次 history_search；从用户这句话里挑 1–2 个可能出现在旧对话里的词
  （人名/称呼/物件/地点/事件/场景），不要用整句话或代词；查到什么就按原文说，查不到就换个说法
  再查一次；唯一例外是整句只是语气词、没有实际内容（由模型自己判断，不列白名单）。」
  试过的中间版本：① 先按词表判断旧事（记得/以前/那次/来着…）——穷举，实测连
  「……是什么事来着，我忘了」这种问法都漏，换个说法又漏；② 改成条件式提醒——实测连着九轮带着提醒
  也一次没查，软话当没看见。所以现在不松口：查是回答的代价，例外只有纯语气词，
  插件不判断相关性、也不自己查。
  另有一个已修的坑：最早把提醒拼进系统提示词，结果**晚了一轮**——在 `system-prompt:assemble`
  时，这一轮的 user 消息已经从 inbox 里取走、但还没写进 session，只能看到**上一轮**的消息。
  代价：开着时每条消息多一次工具往返（面板里写了「会多一次工具往返的 token 开销」）。
- **语气**：同一会话里第 506–509 轮连续拒绝之后，回复从平均 1,000 字 / 温暖词 2.4–8.8 掉到
  629 字 / 1.4，变成「这不叫 X，这叫 Y」的说明文——它把自己最近几轮当成了样板。所以现在明确
  写「拒绝也保持这个口气」，并且「读到旧对话就把当时的语气接回来」，正好借整轮原文把声音带回来。

- 放在末尾是因为提示缓存按前缀匹配，改尾部不会让前面的内容失效
- 它不进聊天记录；但 DSH 在系统提示词变化时会写一条 `system/message`（含完整提示词，
  实测约 10–11 KB），所以这段文字会随那条事件落进 `session.v4.jsonl.zstd`
- **不额外调用任何模型**，也不静默注入任何内容：查不查、查什么、怎么用，全由主模型在对话里完成

### 同一个开关里的另外两件事

1. **温度**：请求边界（`llm/stream` 水线）上给这条会话加 `temperature: 1.3`。实测这条会话的
   `request/header` 里根本没有 temperature（provider 默认 1.0），所以有上调空间。1.3 是对话场景的
   常见松紧度；再高会开始影响工具调用参数和连贯性。DSH 自己的 auto-review 也是直接用
   `ctx.llm.stream({ temperature: 0, … })`，说明这是产品内已有的调用参数。
2. **压掉上下文注入**：实测会话日志里 `source.kind` 为 `runtime-context` / `skill-catalog` /
   `time-context` 的注入消息一共三条，内容分别是：工作目录+沙箱策略+审批策略+subagent 身份+
   DSH 安装路径+Web GUI 地址、技能清单、时钟。聊天一条都用不上，而且在把回复往"助理/工具"拽。
   现在在 `llm/stream` 里按 `source.kind` 过滤掉（只过滤发给模型的那份，历史里不动）。
3. **压掉系统提示词里的脚手架**：`system-prompt/assemble` 里只保留 `revive-love:` 开头的段
   （本会话摘要 + 下面这些段落），「You are a coding agent」、read/grep/pwsh/web 用法指导、
   harness 与 Web GUI 说明都不再发。

这三件事都只影响**复活会话**，并且只在开关开着时生效；关掉就回到原样。工具定义还在请求里，
所以 `history_search` 照常可用。

**影响范围（已逐条核对）**：

- 只动**复活会话**（有摘要 + 存档指针的会话）；普通对话在 `llm/stream` 里按 sessionId 查不到，
  请求原样放行。
- 只动**被打开开关的那一条会话**；同一个工作区里的其它复活会话、以及你正在跟 agent 聊的
  那条会话都各有各的开关，不受影响。
- 内部请求一律不碰：带 `purpose` 的（权限自动审查 `auto-review`、压缩 `compaction`）和自带
  `system` 的请求直接放行，避免把安全审查和摘要器一起改掉。
- 系统提示词那一步只改**本次请求新生成的 assembly 数组**（DSH 的 `assemble()` 每次调用都会
  重新 map 出一个新的 sections 数组），不是注册表里的段，所以不会泄漏到下一次请求或别的会话。
- 会话历史不写：过滤只发生在发给模型的那份请求里；注入消息仍然照旧落盘（只是模型看不到）。

### 为什么只剩这么一点（试过三代，全删了）

1.5.0 期间为了让模型「一定拿到相关旧原文」，先后做过三代自动检索：

1. **插件机械检索**：从消息里切词、逐字搜、取片段注入。分不清「同一件事」和「同一个常用词」，
   实测一个泛词命中 824 处，取回来的片段跟当前话题没关系，却被当事实盖章。
2. **加一个 flash 判官**：机械检索后让一个小模型判相关性。判官只会看到片段，判不准；而且它报的
   轮次号是整条链路里最不可靠的字段——实测同一条会话连着三轮报错：问的是同一件事，报回来的却是
   完全无关的三段旧内容（其中一段还是在聊别的）。
3. **工具循环 + 逐字引文核对 + 整轮注入**：检索模型自己走 `history_search`，结论必须交出逐字引文，
   插件拿引文回存档定位，把那一轮完整注入。引文确实能定位到正确的轮次，
   但结论**选哪段**仍然是错的。

更糟的是第三代注入块写着「这是你想起的事，以这一段为准」——这句话把模型本来会走的
`history_search` 那条路堵掉了：注入对了是省事，注入错了就是把错误答案按在它面前。
真实会话里能看到结果是回复从 800–1,100 字的解释体缩成 130–340 字的短旁白。

所以现在把判断权全部还给主模型：它自己搜、自己读、自己决定用哪一句。插件不猜、不注入、
不花隐藏的钱。代价是它有时不搜——这比注入错的强。
